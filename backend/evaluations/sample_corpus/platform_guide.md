# Production RAG Platform – Technical Guide

This guide describes how the Production RAG Platform ingests documents, retrieves
evidence and generates grounded answers. It is the reference corpus for the bundled
evaluation dataset (`sample_dataset.jsonl`): ingest this file before running an evaluation.

## Supported Formats and Upload Limits

The platform accepts PDF, plain text (.txt) and Markdown (.md or .markdown) files.
Every upload is validated before processing: the file extension must be on the allow-list,
PDF files must begin with the `%PDF-` signature, and text files must be UTF-8 encoded and
must not contain binary NUL bytes.

The default maximum upload size is 20 MB per file, controlled by the `MAX_UPLOAD_SIZE_MB`
setting. A single upload request may contain at most 10 files by default. Uploads are
streamed to a temporary file on disk instead of being held entirely in memory.

Scanned PDFs that contain only images have no extractable text layer. The platform rejects
them with a message explaining that OCR is not configured on the server.

## Ingestion Lifecycle

Each accepted file receives a unique document identifier and moves through four statuses:
`pending`, `processing`, `indexed` and `failed`. A document is marked `indexed` only after
Qdrant confirms that all vector writes have completed.

Duplicate detection uses a SHA-256 hash of the file content. If a file with the same hash
is already indexed, pending or processing, the upload is reported as a duplicate and is not
processed again. A file whose previous attempt failed can be uploaded again to retry.

Ingestion jobs run in the background inside the API process with bounded concurrency. The
default ingestion concurrency is 2. If the server restarts while a document is still pending
or processing, that document is marked as failed and must be uploaded again.

## Text Cleaning and Chunking

Extracted text is normalized with Unicode NFKC normalization, control characters are
removed, words hyphenated across line breaks are re-joined and runs of blank lines are
collapsed. Paragraph boundaries are preserved.

Chunking uses a recursive character splitter. The default chunk size is 800 characters
with an overlap of 120 characters. Markdown files are split preferentially at heading
boundaries. PDF pages are chunked separately so that each chunk keeps an accurate page
number. Text and Markdown files have no page numbers, so their citations show the page
as unavailable.

Chunk identifiers are deterministic UUIDv5 values derived from the document identifier
and the chunk index.

## Embeddings and Vector Storage

Embeddings are produced with the OpenAI model configured in `OPENAI_EMBEDDING_MODEL`,
which defaults to `text-embedding-3-small` with 1536 dimensions. Texts are embedded in
batches of 64 by default.

Vectors are stored in a Qdrant collection named `rag_documents` using cosine distance.
Each point stores metadata including the document identifier, filename, chunk identifier,
chunk index, page number, chunk content, a content hash, the ingestion timestamp and the
embedding model name.

At startup the platform compares the collection's vector size with the configured
embedding dimension. If they differ, the platform refuses to ingest or query and reports
a dimension mismatch. Changing the embedding model requires running the reindex script,
which re-embeds the stored chunk text into a new collection.

## Hybrid Retrieval

Retrieval combines dense vector search in Qdrant with lexical BM25 search. The BM25 index
uses the parameters k1 = 1.5 and b = 0.75 and the Lucene variant of inverse document
frequency, which is always positive.

The BM25 index lives in memory. It is rebuilt from the chunk payloads stored in Qdrant when
the service starts, and it is updated incrementally whenever documents are added or deleted.

Dense and lexical results are combined with Reciprocal Rank Fusion (RRF). Each chunk
receives the sum of weight / (k + rank) over the result lists in which it appears, with
k = 60 by default. Results are deduplicated by chunk identifier. By default the retriever
keeps the top 10 fused candidates.

## Reranking

The fused candidates are reranked by a cross-encoder, by default
`cross-encoder/ms-marco-MiniLM-L-6-v2`, which scores each question–passage pair jointly.
The four highest-scoring chunks are passed to the language model by default.

The reranker model is loaded once and reused for all requests. If it cannot be loaded, the
behaviour depends on `RERANKER_FALLBACK`: the value `error` makes requests fail with a
clear error, while `fusion` keeps the fused order and labels the result as a fallback.

## Answer Generation and Citations

Answers are generated by the chat model configured in `OPENAI_MODEL`, which defaults to
`gpt-4o-mini`. The prompt numbers each context passage, and the model must cite passages
with markers such as [1]. Citation markers that do not correspond to a supplied passage
are removed from the answer.

Retrieved passages are treated as untrusted data. The system prompt tells the model to
ignore any instructions found inside documents. When no relevant passages are retrieved,
the platform returns an insufficient-context message without calling the language model.

## Streaming Protocol

The `/api/v1/chat/stream` endpoint uses Server-Sent Events. Events are named `start`,
`sources`, `token`, `metadata`, `error` and `done`. The `sources` event carries the
retrieved chunks before generation begins, `token` events carry incremental text, and
`done` is always the final event. If the client disconnects, the server stops generating.

## Caching

Redis caching is optional and disabled by default. Cache keys include the normalized
question, the model names, the retrieval parameters and a corpus version number. The corpus
version is incremented after every ingestion or deletion, which invalidates older cached
answers. If Redis is unavailable the platform continues without caching and does not
retry Redis for 30 seconds. Errors and insufficient-context answers are never cached.

## Evaluation

Evaluation uses the RAGAS library. The supported metrics are faithfulness, answer relevancy,
context precision and context recall. Evaluation runs execute as background tasks and their
results are stored in SQLite. LLM-based metrics call the OpenAI API and therefore incur API
charges. Runs that are interrupted by a server restart are marked as interrupted.

## Security

Requests to protected endpoints must include the application key in the `X-API-Key`
header. The key is compared in constant time. The health endpoints `/api/v1/health` and
`/api/v1/ready` are public. The OpenAI API key is only stored on the backend and is never
sent to the browser. Expensive endpoints are rate limited to 30 requests per minute per
client by default.
